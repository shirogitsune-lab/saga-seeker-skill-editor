# Treat profile `<br>` elements as semantic newlines

## Context

Game-exported character sheets represent line breaks in the seven profile
fields differently in their two synchronized representations:

- JSON strings contain CR, LF, or CRLF characters; and
- direct profile `div.tab-content` children use HTML `<br>` elements.

The loader previously accepted only HTML content without any tag. A profile
whose JSON contained a newline and whose HTML contained the equivalent `<br>`
was therefore classified as read-only even though the two values had the same
display meaning.

The original-sheet preservation contract still applies. Loading a sheet must
not rewrite its bytes, normalize its stored JSON, or create draft edits merely
because line endings have different spellings.

## Decision

Profile diagnosis compares semantic display text:

1. Decode the direct profile element content as UTF-8.
2. Convert only attribute-free `<br>`, `<br/>`, and `<br />` elements,
   case-insensitively, to LF.
3. Reject attributes, comments, and every other HTML element instead of
   interpreting or stripping them.
4. Decode HTML character references.
5. Normalize CRLF and lone CR to LF in both the JSON value and decoded display
   value for comparison only.

An unchanged sheet retains its original bytes and line endings. The normalized
comparison value is not written into the source data or draft.

When a user explicitly edits a profile value, its exact string is written to
the JSON token through the existing script-safe serializer. The matching HTML
content is generated by normalizing that edited value's display newlines to LF,
escaping it as HTML text, and replacing each LF with canonical `<br>`.

This rule applies only to the seven profile fields. It does not broaden the
accepted markup for names, skills, memories, or other sections.

## Compatibility evidence

A read-only anonymous audit covered 162 local HTML files. One file was not a
loadable character sheet; all 161 loadable sheets used only attribute-free
`<br>` tags in their profile content.

After applying this decision, 115 of the 161 profiles matched exactly under the
defined newline semantics and became editable. The remaining 46 retained a
JSON/HTML mismatch: 39 differed by outer whitespace, six omitted one or more
internal newlines in HTML, and one contained different non-whitespace content.
Those differences are not silently trimmed, collapsed, or repaired. They
remain read-only pending a separate, explicit compatibility decision.

The audit rehashed every source after loading and confirmed that all source
bytes were unchanged.

## Consequences

- Existing game sheets using `<br>` for profile line breaks remain editable.
- LF, CRLF, and lone CR compare as the same displayed line break without
  mutating an unopened or unsaved value.
- Explicitly edited JSON strings retain the input newline spelling, while the
  generated HTML uses one canonical `<br>` spelling.
- Any profile HTML beyond plain text, character references, and the three
  supported `<br>` spellings remains read-only.
